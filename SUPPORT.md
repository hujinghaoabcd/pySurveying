## Usage questions

For a usage question, open a GitHub issue only when the answer is not already covered by the documentation.

Please include:

- the function you are using;
- a minimal code/data example;
- coordinate and angle conventions;
- units;
- the result you expected;
- the result you obtained.

## Bug reports

Use the bug-report issue template. A reproducible test case is the fastest way to get a numerical problem reviewed.

## Feature requests

Use the feature-request template and explain the surveying workflow that is missing rather than only naming a function.

The project intentionally keeps a limited scope, so large new subsystems may be declined or deferred even if they are useful in a broader surveying platform.

## Validation/reference contributions

Independent reference cases are especially valuable. If you have a textbook, specification, paper, or trusted software result that can be redistributed or clearly described, include:

- source information;
- full conventions;
- input data;
- expected output;
- tolerances/precision shown by the source.

## Security

Do not report vulnerabilities with exploit details in a public issue. Follow [`SECURITY.md`](SECURITY.md).

## Production surveying

pySurveying is open-source computational software, not a certification of compliance with any particular cadastral, metrology, national-control, or legal-survey specification. Users remain responsible for independent verification against the specification that governs their work.
